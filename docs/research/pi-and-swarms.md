## Executive summary

- **Pi is a layered, relatively narrow runtime.** `pi-ai` handles provider/model access; `pi-agent-core` supplies a generic agent/event loop; `pi-coding-agent` owns the coding CLI, session orchestration, tools and extensions; `pi-tui` is separately usable terminal UI infrastructure. The normal coding-agent session persists an append-only JSONL event/tree history. A separate `pi-durable` + Chord harness is explicitly experimental and provides a stronger commit-before-visible, checkpoint/recovery/task model. These are distinct durability contracts, not interchangeable descriptions of one session implementation. ([package workspace](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/package.json), [agent core exports](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/agent/src/index.ts), [AgentSession](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/agent-session.ts), [SessionManager](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/session-manager.ts), [durable README](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/durable/README.md))
- **Swarms is a broad Python toolkit organized around a configurable `Agent` plus many independently selectable orchestration classes.** Its current `SwarmRouter` source enumerates multiple supported orchestration classes, while workflows use distinct data-flow and failure policies. The breadth is useful as a pattern library but does not mean each topology shares one uniform state, persistence, or failure contract. ([Agent](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/agent.py), [SwarmRouter](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/swarm_router.py), [ConcurrentWorkflow](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/concurrent_workflow.py), [MixtureOfAgents](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/mixture_of_agents.py))
- **Folie fit:** Pi's package seams, event vocabulary, transcript projection/branching, and explicit durable task lifecycle are the most relevant patterns. Keep Folie's ax sandbox and Postgres single-writer authoritative; do not adopt Pi's local JSONL as a second source of truth or infer that its durable runtime is production-stable. Swarms' explicit workflow topologies and bounded worker concurrency are candidates for small isolated experiments, not a framework migration.
- **Security distinction:** Pi's project trust gates project-local executable/resource loading; it is not a process sandbox. Swarms' MCP deployer implements a separate HTTP authentication layer, but any exposed agent still carries the permissions of its host process. ([Pi trust manager](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/trust-manager.ts), [MCPDeployer](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/mcp_deployer.py))

A useful call chain for the ordinary CLI is: input/mode → `AgentSession` → core agent loop → `pi-ai` stream → tool call outcome through coding-agent's tool definitions → session/event updates → mode renders. It is a layered composition, not proof each package can independently own the full application lifecycle. ### Ordinary runtime, tool and event lifecycle

`AgentSession` wraps core Agent state and subscribes to core events, adding session-specific events for appended entries, queue changes, compaction, retries and settlement. It owns model/thinking selection, session switching/branching, tool/event wiring and compaction; UI/business logic remains outside the core generic loop. ([AgentSession types and event union](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/agent-session.ts), [core agent loop](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/agent/src/agent-loop.ts))

At a high level, a user prompt is accepted by the session/mode, contextual messages and tools are assembled, `pi-agent-core` asks the selected stream function for an assistant response, and tool-call messages are passed through tool-call lifecycle handling and executed. Results become messages/events consumed by the next loop iteration; final/settled state and usage are reflected in session events. The exact event contracts matter: core `AgentEvent` is distinct from the larger session event union. ([agent-core event/type definitions](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/agent/src/types.ts), [AgentSession](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/agent-session.ts), [tool call wrapper](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/agent/src/agent.ts))

Built-in tools are defined by coding-agent and use the session environment/context; extension tools can be wrapped alongside them. Tool execution can emit start/update/end events and failures become tool outcomes rather than silently disappearing. ([coding-agent tool registry](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/tools/index.ts), [AgentSession tool/event definitions](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/agent-session.ts), [extension runner](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/extensions/runner.ts))

### Coding-agent persistence and durable alternative

**JSONL sessions:** `SessionManager` stores a header and typed entries with `id` and `parentId`. Entries include messages, model/thinking changes, usage, compaction and branch summaries, custom entries/messages, context edits, labels and session metadata. Parent links represent branches; projection builds the model-visible transcript rather than requiring every stored entry to be sent to the model. `CustomEntry` stores extension state but is not LLM context; `CustomMessageEntry` can participate in context. The append-only representation makes tree navigation and replay/projection possible, but should not be conflated with database transactions or durable exactly-once side effects. ([SessionManager types](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/session-manager.ts), [session manager implementation](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/session-manager.ts), [session branching tests](https://github.com/earendil-works/pi/tree/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/test))

The interactive session lifecycle includes resume, fork/switch/tree navigation, compaction summaries and branch summaries; compaction edits what is included in effective context while retaining transcript structure. ([AgentSession](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/agent-session.ts), [compaction implementation](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/compaction), [session manager](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/session-manager.ts))

**Durable harness:** `packages/durable/README.md` labels the API experimental and states the central contract: commits are atomic, an input/task is durably admitted before work is displayed, tasks checkpoint state, and reopening/resume schedules unfinished work. Conversation transcript entries are immutable; typed documents hold agent selection, provider identity, live generation/tool state, inbox and usage. One generation task owns tool tasks, waits for them, then continues generation. Storage backends include in-memory, SQLite and JSONL (the README's persistence section documents adapters). ([durable README](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/durable/README.md), [durable storage package](https://github.com/earendil-works/pi/tree/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/durable/src/storage), [durable task/harness code](https://github.com/earendil-works/pi/tree/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/durable/src/harness))

Durable tool calls have a persisted intent and explicit replay policy: a process interruption reruns only tools declared replay-safe; otherwise the caller receives an interrupted result. Retry/backoff, restart limits and reports are represented by durable task state, not merely an in-memory retry loop. That still does not make arbitrary external side effects exactly once: replay-safety is an application/tool declaration and should be assessed per side effect. ([durable README: tools and failures](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/durable/README.md), [tool task implementation](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/durable/src/harness/tool.ts), [scheduler](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/durable/src/harness/scheduler.ts))

### Extensions, trust, and UI lifecycle

Coding-agent extensions are dynamically loaded and can register tools/commands, subscribe to lifecycle events, and interact with the UI. Event coverage spans input preparation, agent/turn/provider/message/tool/session lifecycle; some handlers are observational while others can transform, replace or block actions. A `tool_call` guard failure fails closed for that call. ([extension API](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/extensions/index.ts), [extension runner](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/extensions/runner.ts), [extension docs](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/docs/extensions.md))

Project trust gates project-local resources that can affect execution—settings, MCP config, extensions, skills, prompts, themes, and system prompt files. This prevents silent project extension loading, but extensions execute in-process with the host's permissions; trust gating is not isolation. Use ax (Folie's sandbox) as the actual OS-level boundary. ([trust manager](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/trust-manager.ts), [extension docs/security](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/docs/extensions.md))

The interactive mode is an IO/rendering layer over `AgentSession`. It composes `pi-tui` components; `TuiMainScreen` supports inline mode and `TuiAltScreen` alternate-screen/full-screen mode. Components render terminal lines, while TUI handles input dispatch, focus, overlays and differential redraw. The extension `ctx.ui` surface can surface dialogs, notifications, widgets and custom UI. These seams are relevant because Folie already has a full-screen OpenTUI surface: borrowing the runtime/event integration idea is lower risk than replacing the surface. ([InteractiveMode](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/modes/interactive/interactive-mode.ts), [TUI renderer choice](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/modes/interactive/tui-renderer.ts), [pi-tui](https://github.com/earendil-works/pi/tree/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/tui/src), [extension API](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/extensions/index.ts))

## Swarms architecture

### Agent abstraction and task/message/state flow

The `Agent` class is a large configurable Python abstraction combining LLM management, tool management, conversation/memory, optional planning, context compression, skills, streaming and execution control. Constructor options include model/LLM, tools, max loops, retry/fallback models, persistent memory/autosave, workspace, output formatting, MCP connections and channel communication. `run()` accepts a task, and its internal execution path builds/updates conversation input, calls the model, executes tool outcomes, appends results, checks stopping conditions, and returns formatted output. `max_loops="auto"` delegates to a separate autonomous loop. ([Agent source](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/agent.py), [LLMManager](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/agents/llm_manager.py), [ToolManager](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/agents/tool_manager.py), [Conversation](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/conversation.py), [autonomous loop](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/agents/autonomous_loop.py))

Memory is not a single uniform backend. Conversation history/short memory is distinct from optional persistent `MEMORY.md`, vector-store/long-term memory, and a shared `CommsChannel`. Tool execution and MCP management are separate subsystems. The configured workspace/autosave paths matter operationally; do not assume that every object state needed for restart is automatically captured by the conversation. ([Conversation](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/conversation.py), [Agent](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/agent.py), [memory package](https://github.com/kyegomez/swarms/tree/5172a9d2defb2c92702214388952a640daef3f3e/swarms/memory), [comms channel](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/comms_channel.py))

### Orchestration patterns and flow

It supports optional ordered fallback swarm types when an attempted run raises; this is workflow-level fallback, not a universal agent-level retry contract. ### Tools, memory, concurrency, retries and failure

`ToolManager` and tool-related modules provide the Agent's tool surface; MCPManager normalizes MCP server connections and routes calls. Agent-level retry attempts/fallback models are separate from orchestration failure behavior. A topology may catch/store/omit/raise individual failures or allow router fallback, depending on that class. This variability argues for Folie-owned explicit task outcomes rather than copying an implicit “retry everything” policy. ([ToolManager](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/agents/tool_manager.py), [MCPManager](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/tools/mcp_manager.py), [Agent](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/agent.py), [ConcurrentWorkflow](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/concurrent_workflow.py), [SwarmRouter](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/swarm_router.py))

### Security and limits

Swarms' MCP server layer can authenticate HTTP requests, and its MCP client side supports auth configuration. ## Folie implications and prioritized experiments

Folie context supplied for this research: ax sandbox, message-only wake semantics, Postgres sole-writer, pi runtime, and an existing full-screen OpenTUI surface. The recommendations below are implications for that architecture, not a request to adopt either framework wholesale.

### Worth borrowing

1. **High value / low risk — define an explicit runtime-to-UI event contract.** Pi's layered session event stream can give OpenTUI stable lifecycle events (prompt admitted, model/turn start/end, tool start/update/result, queued/settled, error/retry, compaction). Keep rendering state derived from authoritative persisted events; UI should not become a second execution controller. ([AgentSession events](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/agent-session.ts), [core event types](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/agent/src/types.ts))
2. **High value / low risk — explicit typed task/tool outcomes and idempotency.** Pi durable's request IDs, immutable entries, committed admission and replay declaration make crash semantics legible. Adapt these concepts to Postgres/ax: stable operation ID, persisted intent/result, explicit retryability, and deterministic interrupted/error outcomes. Keep Postgres the one writer; do not adopt Chord or duplicate store. ([durable README](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/durable/README.md), [tool code](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/durable/src/harness/tool.ts))
3. **High value / medium risk — model message-only wake as a durable scheduling signal, not a work payload.** Durable harness separates durable task/sleep state from host wake/alarm and says wake signals active/earliest time. [INFERENCE] This resembles Folie's constraint: the message can notify a process that persisted Postgres state may be runnable, while it remains the database—not queue message—the source of truth. Validate duplicate/out-of-order/missed wake behavior against Folie's own protocol. ([durable README: sleeping and waking](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/durable/README.md))
4. **Medium value / low risk — use explicit bounded fan-out patterns only for independent work.** Swarms concurrent workflow exposes `max_workers` and an explicit per-agent error policy; MoA has a concrete layered fan-out/fan-in pattern. Trial for a Folie task where parallel results are useful, with Postgres claim limits and ax resource caps controlling concurrency. ([ConcurrentWorkflow](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/concurrent_workflow.py), [MoA](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/mixture_of_agents.py))
5. **Medium value / medium risk — keep project configuration trust separate from sandbox enforcement.** Pi's trust gate is a useful UX gate for project executable resources; ax remains the security boundary. Require explicit approval/allowlisting before user/project extensions or MCP tools become executable. ([trust manager](https://github.com/earendil-works/pi/blob/c5d3978350c7d32db5d8eb28400d4fa851624703/packages/coding-agent/src/core/trust-manager.ts))
6. **Lower value / low risk — use only topology-specific vocabulary.** Sequential, concurrent, hierarchical, and MoA have different semantics. Name Folie operations by their actual dataflow and failure behavior rather than introducing one generic “swarm” abstraction. ([SwarmRouter](https://github.com/kyegomez/swarms/blob/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs/swarm_router.py), [workflow implementations](https://github.com/kyegomez/swarms/tree/5172a9d2defb2c92702214388952a640daef3f3e/swarms/structs))

### Conflicts and risks

- **Persistence conflict:** Pi's JSONL and Swarms' workspace/autosave are not Folie's Postgres; dual authoritative stores risk divergence. Treat exports/caches as projections only.
- **Wake semantics conflict:** Do not let a durable scheduler/agent directly wake itself through an independent timer or queue if Folie requires message-only wake. A stored due-time can be a wake decision only if its notification respects Folie's message contract.
- **Writer conflict:** Parallel worker calls are compatible with a single writer only if workers return results to a serialized Postgres commit path; they must not independently mutate authoritative records.
- **Sandbox risk:** Pi extensions and Swarms tools execute in host process contexts; neither project trust nor MCP auth replaces ax isolation.
- **Retry risk:** Replaying a tool or falling back to another model can duplicate side effects/cost. Define idempotency/replay policy per tool and persist attempt/terminal outcome.
- **UI risk:** Pi's `pi-tui` is not OpenTUI. Its event/render architecture is a pattern to adapt, not a mandate to replace Folie's full-screen UI.
- **Breadth risk:** Swarms has topology options but varied error/state contracts; copy a specific proven algorithm, not its broad abstraction surface.

## Open questions for Folie

1. Which exact persisted Postgres records define a runnable item, and what idempotency key binds message admission to the pi run?
2. Does the message-only wake channel guarantee delivery, ordering, duplication, or only best-effort signaling? What reconciliation path detects a lost wake without polling violations?
3. Which tool side effects are replay-safe under ax restart, and which require explicit user confirmation or compensation?
4. What event payloads may reach OpenTUI, and which must be redacted before persistence/telemetry?
5. Would any real Folie workload benefit from parallel fan-out, or does single-writer serialization erase enough benefit that sequential pi tasks are preferable?
6. Which pi durable features are currently relied upon in Folie's runtime versus only studied? Its README explicitly marks the API experimental.
